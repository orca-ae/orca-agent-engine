# Overview

## Context

Anthropic's beta Managed Agents API runs every agent session on Anthropic's hosted infrastructure: customers pay Anthropic for execution and Anthropic owns the runtime, the egress, and the audit trail. Orca's goal — governed identity, governed egress, governed state, all inside one workspace — cannot be met while the agent runtime sits outside the workspace.

This work introduces a **self-hosted** managed agent provider that mirrors the Anthropic Managed Agents beta API surface (`managed-agents-2026-04-01`) closely enough that the official Anthropic SDKs can point at it, but runs inside an Orca workspace on infrastructure the operator runs:

- Kafka (Apache Kafka or any Kafka-compatible backend) for the default event log; Postgres and Apache Pulsar are supported alternatives for self-hosted deployments.
- Postgres for relational metadata.
- A purpose-built MCP egress gateway.
- Pluggable sandbox runtimes (local, E2B, OpenSandbox, AgentENV) for the agent's "hands."

The system is built around three in-repo deployable services, one package that
ships inside sandbox images, five in-repo libraries, and one external gateway
image:

- `services/registry-service-ts/` — TypeScript HTTP service exposing the Anthropic-compatible REST + SSE API. Control plane, and the shared server that coordinates `colocated` sessions over the WS tunnel.
- `services/harness-server/` — TypeScript service that hosts active session loops via a pluggable `AgentHarness` (Claude Agent SDK, Codex SDK, and Pi SDK). Internal-only; runs the `separate` mode (see [`architecture.md`](./architecture.md)).
- `services/session-runner/` — TypeScript service: the `colocated` engine. Runs the agent loop and its tools together inside the sandbox; dials the registry over the WS tunnel. See [`harness-modes.md`](./harness-modes.md) and [`deployment-topologies.md`](./deployment-topologies.md).
- `services/sandbox-harness/` — `@orca/sandbox-harness`: the HTTP/SSE server baked into per-harness sandbox images so a `colocated` harness process can be driven from `harness-server`. An image payload, not a cluster service.
- `packages/transcript-store/` — TypeScript library: append-only session/event log over Kafka, Postgres, or Pulsar.
- `packages/file-store/` — TypeScript library: file blobs (object store + Postgres metadata, SHA-256 dedup).
- `packages/memory-store/` — TypeScript library: path-addressed text memory with immutable versions.
- `packages/skill-store/` — TypeScript library: immutable, digest-addressed
  Skill bundles for Registry writes and Harness reads.
- `packages/harness-catalog/` — TypeScript library, pure data: the single source of truth for harness types, supported modes, default sandbox images, and ports.
- `ai-gateway` — external `ghcr.io/orca-ae/orca-ai-gateway` image: vault-aware MCP egress that resolves `credential_id` → backend credentials and proxies to upstream MCP servers, plus the LLM path for `colocated` harnesses.

**Outcome:** customers can keep using the Anthropic SDK (`anthropic.beta.agents.sessions.*`) but point its `base_url` at an Orca workspace. The same agent code runs, but every event, every tool call, and every credential stays inside the workspace.

## Confirmed decisions

| Decision                | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Componentization        | TypeScript service runtimes live under `services/` (`registry-service-ts`, `harness-server`, `session-runner`, `environment-worker`, `observability-exporter`), alongside `sandbox-harness` (an image payload, not a cluster service); store and support code lives as TypeScript libraries under `packages/`; MCP egress is consumed as an external `ghcr.io/orca-ae/orca-ai-gateway` image. Registry internal calls use projected ServiceAccount JWT + TokenReview in Kubernetes and a shared service token elsewhere; mesh mTLS remains transport defense-in-depth.                   |
| Gateway topology        | Use the external `ghcr.io/orca-ae/orca-ai-gateway` image, available as a public image under Apache-2.0, for managed-agents traffic.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| API scope               | Mirror Anthropic beta surface for: Agents, Environments, Sessions, **Files**, **MemoryStores** (with nested memories + memory_versions), Vaults, Skills (versioned, fully first-class), and Session-`resources[]` polymorphic mounts (file / memory_store / github_repository). SSE streaming included. Orca additionally owns the `orca-extension` `/v1/triggers` cron surface; it is not wire-compatible with Anthropic Deployments. **Outcomes are out of scope for v1** — the field exists on Session for SDK compatibility (returns null) but no execution semantics.   |
| Sandbox runtime         | Pluggable `SandboxRuntime` interface with five implementations: `local` (host shell wrapped by `srt`), `e2b` (E2B cloud sandboxes), `opensandbox` (OpenSandbox server), `agentenv` (AgentENV Firecracker VMs), and `in-memory` (tests). Selected by the **required** `SANDBOX_RUNTIME` env var on `harness-server` — there is no silent default; `loadConfig` throws on a missing or unrecognized value.                                                                                                                                                                     |
| Event storage           | `@orca/transcript-store` is pluggable. Kafka topic-per-session is the default; retention and tiered storage are the operator's broker configuration on Apache Kafka or any Kafka-compatible backend. Postgres can be selected with `TRANSCRIPT_STORE_BACKEND=postgres` for local, test, and smaller self-hosted deployments. Apache Pulsar can be selected with `TRANSCRIPT_STORE_BACKEND=pulsar` for Pulsar-native workspaces. No dual-write mirror in v1: the selected backend is the source of truth.                                                                             |
| File storage            | Object store (S3/GCS/Azure Blob/MinIO) for bytes + Postgres for metadata + content-addressed dedup (SHA-256). Behind the `@orca/file-store` library API.                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Memory storage          | Postgres-backed text-document store (path-addressed; not vector). Workspace-scoped. Immutable version chain per memory; versions are retained indefinitely (nothing expires them today). Behind the `@orca/memory-store` library API.                                                                                                                                                                                                                                                                                                                                        |
| Skill storage           | Private immutable bundle objects in S3/MinIO behind `@orca/skill-store`; Postgres holds manifests and exact Session bindings. Harness materializes verified bundles read-only and exposes only a compact name/description/path catalog until the model chooses to read a Skill.                                                                                                                                                                                                                                                                                              |
| Transcript store        | TypeScript library with Kafka, Postgres, and Pulsar backends. Append/read/tail of opaque-payload events. A session is bound to one harness for life — no cross-harness interop. The harness owns payload semantics.                                                                                                                                                                                                                                                                                                                                                          |
| Harness pluggability    | Pluggable `AgentHarness` interface. Two topologies are supported: **`separate`** (Claude Agent SDK runs in `harness-server`, tools dispatched to sandbox — v1 default) and **`colocated`** (the agent loop and its tools run together inside the sandbox, driven by `session-runner`, coordinated by the registry as the shared server over the WS tunnel — v1 for `claude_code`). The topology is selected by `metadata.harness` + `metadata.mode` on the agent. See [`harness-modes.md`](./harness-modes.md) and [`deployment-topologies.md`](./deployment-topologies.md). |
| LLM egress              | **`separate` path:** a Session's `metadata.orca_llm_egress` (`direct` or `gateway`) wins; otherwise the deployment's `LLM_EGRESS_DEFAULT` applies (chart `harness.llmEgressDefault`, `direct` when unset). `direct` calls the model provider from `harness-server` with its own provider key (the Claude Agent SDK calls `api.anthropic.com`); `gateway` sends model calls through the ai-gateway at `LLM_GATEWAY_URL` with a Session-scoped JWT. **`colocated` path:** always the ai-gateway — the in-sandbox harness receives a per-session JWT as `LITELLM_API_BASE` / `LITELLM_API_KEY` (`harness-server/src/harness/in-sandbox/llm-env.ts`); no provider keys enter the sandbox. |
| Inbound auth            | Accept both `x-api-key` (Anthropic-SDK compat) and OIDC/JWT (first-party Orca clients).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Management authority    | Use separate Platform Admin and organization-admin principals. Platform Admin has no organization scope and can call only `/v1/platform/*` to create organizations and workspaces. Organization admins derive exactly one organization from their credential and retain the Anthropic-aligned `/v1/organizations/*` surface. Key prefixes, tables, fingerprint domains, authenticators, OIDC audiences, audit logs, and idempotency namespaces are separate.                                                                                                                 |
| Vault flow              | `registry-service` owns Vault metadata and nested credentials. Sessions reference `vault_ids[]`; credentials under those vaults bind to MCP servers by `auth.mcp_server_url`. `harness-server` redirects MCP traffic through `ai-gateway` with `X-Orca-Credential-Id`. The gateway resolves `credential_id` via an internal registry endpoint and injects outbound auth. Credentials never enter the sandbox or the harness process.                                                                                                                                         |
| Tool-name normalization | Accept `agent_toolset_20260401` from Anthropic-SDK clients for compat; internally and in our own surface use the vendor-neutral name **`agent_toolset`**. Same applies to other Anthropic-dated identifiers.                                                                                                                                                                                                                                                                                                                                                                 |
| Versioning header       | We use **`orca-beta`**, NOT `anthropic-beta`. The SDK's auto-injected `anthropic-beta: managed-agents-2026-04-01` is silently ignored. We are not Anthropic and don't want the SDK to think we are.                                                                                                                                                                                                                                                                                                                                                                          |
| Idempotency (day-one)   | Every write endpoint accepts `Idempotency-Key` header. `POST /v1/sessions/{id}/events` additionally honors a `request_id` field on each event for batch-level idempotency. `transcript-store.Append` dedupes by `Event.id`. `ai-gateway` and `memory-store` each cache idempotency keys for 24 h with the result body. Tested on every write path in CI.                                                                                                                                                                                                                     |
| MCP routing             | The harness rewrites `agent.mcp_servers[*].url` to point at `ai-gateway` at session-start time, encoding the original backend identity in `X-Orca-Backend` header and a session-scoped JWT in `Authorization`. Claude Agent SDK accepts the rewritten config via its `mcpServers` option — no SDK fork. See [`mcp-routing.md`](./mcp-routing.md).                                                                                                                                                                                                                            |
| Resource mounting       | Harness materializes resources through `MountStrategy`: host-side tarball prefetch for files (the sandbox never sees the file-blob namespace), FUSE where supported for memory stores and execution outputs, host-side clone + stream for GitHub. GitHub `authorization_token` is write-only, materialized into SecretStore, and never returned or placed in the sandbox. In-sandbox HTTPS push/fetch uses Orca's session-JWT credential helper. See [`resource-mounting.md`](./resource-mounting.md).                                                                       |

## Engineering principles adopted from Anthropic's Managed Agents post

The Anthropic engineering post (https://www.anthropic.com/engineering/managed-agents) articulates the design pattern that makes managed agents production-grade. We adopt them as load-bearing constraints on this design, not as nice-to-haves. Each principle maps to a specific architectural choice below.

| Principle                                                           | How we apply it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Brain / hands / session decoupled**                               | Brain (LLM call) lives in `harness-server` and reaches the model provider directly or through `ai-gateway`, per the Session's LLM egress. Hands (tool execution) split into `ai-gateway` (MCP egress) + `SandboxRuntime` (built-in toolset, E2B v1). Session (state) lives in `transcript-store`, plus `file-store` and `memory-store` for the agent-visible filesystem. None of these has a hard runtime dependency on another's implementation — only on its public API.                                                                                                                                                                        |
| **Never embed credentials in sandboxes**                            | Vault credentials are resolved at `ai-gateway` from a `credential_id` header; they never enter the harness process or the sandbox container. Same pattern for any future credential class — credentials are a gateway concern.                                                                                                                                                                                                                                                                                                                                                             |
| **Cattle, not pets**                                                | All long-running workloads are stateless. Sessions are durable in Kafka and reattach to any healthy harness replica via Kafka consumer group redelivery. Replicas can be restarted, replaced, or scaled at any time.                                                                                                                                                                                                                                                                                                                                                                       |
| **Lazy provisioning**                                               | Sandbox is **not** allocated at Session creation. Harness allocates it when execution first needs sandbox state: a Skill bundle, a Session resource, or an `agent_toolset` tool call.                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Event-log replay over reconstructed state**                       | The selected transcript backend is the source of truth. Session resume reads the log and lets the harness rebuild context from it; we don't snapshot working memory or marshal mid-state structures.                                                                                                                                                                                                                                                                                                                                                                                       |
| **Uniform tool interface**                                          | Every tool, regardless of source, normalizes to `(name, input) -> result` at the harness boundary. The harness doesn't know whether a tool ran in the sandbox, against an MCP server through the gateway, or as a custom-tool callback to the client.                                                                                                                                                                                                                                                                                                                                      |
| **Don't bake model-specific context strategies into the harness**   | The harness orchestrates events and dispatches tools; it does not own context-window management, summarization, or compaction. Those live inside the SDK. When we add a non-Claude harness, we don't pull its context strategy into our common code.                                                                                                                                                                                                                                                                                                                                       |
| **Permission policies as data**                                     | Tool-level `permission_policy` is the Anthropic wire object (`{ type: "always_allow" }` / `{ type: "always_ask" }` / `{ type: "always_deny" }`) on the Agent record, including `mcp_toolset.default_config` and per-tool `mcp_toolset.configs` entries. Tool-confirmation events flow through the same event log. No permission code is special-cased per harness.                                                                                                                                                                                                                         |
| **Permission policies are guardrails**                              | A tool-level `permission_policy` is the stateless, agent-scoped, tool-name-keyed case of a Guardrail. One decision per action, produced by one fold over `allow < ask < deny` seeded by the permission policy, so composition can only tighten. Guardrails generalize it to four authority tiers, to state that accumulates, and to predicates over tool input, usage, and model. The `permission_policy` wire shape is unchanged. See [`guardrails.md`](./guardrails.md). This is governance data, not context strategy — it does not conflict with the context-strategy principle above. |
| **Observability via the event log, not by SSH'ing into containers** | Operators read sessions by tailing the selected transcript backend via `transcript-store`. Sandboxes are sealed; nobody attaches to a running container in production. All audit (ai-gateway calls, file-store reads/writes, memory edits) is emitted as events on dedicated Kafka topics — same substrate, same tooling.                                                                                                                                                                                                                                                                  |
| **Horizontal scale via stateless harnesses**                        | `harness-server` replicas share work through the selected backend: Kafka consumer groups on session topics, Postgres lease claims on `transcript_event_claims`, or Pulsar `KeyShared` subscriptions. No sticky routing, no per-session control plane.                                                                                                                                                                                                                                                                                                                                           |

The Anthropic post also stresses **token brokering**, **idempotency**, and **versioning** of agents/environments. We pick those up explicitly in component design (vault flow, idempotency keys on `POST /events`, version-on-update for Agents and Skills).
