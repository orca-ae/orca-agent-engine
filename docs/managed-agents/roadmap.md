# Roadmap

**This is the only document that describes work not yet done.** Every other doc under `docs/`
describes what the code does today, in the present tense. If you are deferring something, add it
here with its trigger rather than leaving a note in a design doc — see `AGENTS.md` → Hard rules.

Each entry states what it is, why it is not built, and — where one exists — the condition that
would make us build it.

> **Load-bearing headings.** `services/registry-service-ts/conformance-decisions.yaml` points four
> rules at [`#anthropic-surface-not-implemented`](#anthropic-surface-not-implemented) and one at
> [`#environment-work-stats-path-and-shape`](#environment-work-stats-path-and-shape).
> `pnpm conformance:gen` resolves every `reference:` to a real file _and anchor_, and exits 1 when
> one does not resolve — so renaming either heading fails the `test` job. A pull request that changes
> only Markdown outside `services/` and `packages/` skips that job (`.github/scripts/changed-areas.sh`),
> so the failure then surfaces on the next change that runs it. (The generated matrix itself would
> stay byte-identical: it prints the reference string, it does not follow it.) Update the register in
> the same commit if you must.

**How this register relates to proposals.** Work that needs design review starts as an
[Orca Improvement Proposal](../../proposals/README.md) (OIP). While an OIP is proposed or being
implemented it is listed under [In progress](#in-progress); once it ships, it leaves this page and its
OIP stays as the design record. A pull request that ships, defers or drops work listed here edits
this page in the same pull request, and a pull request that changes an OIP's status updates the OIP
and its row in the proposals index together.

- **OrcaAgent SDK.** A runtime SDK that lets an agent written with any framework run as a

## Kafka transcript Schema Registry

The optional envelope codec and its deployment settings are described in
[transcript-store](./libraries/transcript-store.md#optional-kafka-avro-envelope).
The following extensions are not implemented:

- **History migration and seamless per-session encoding cutover.** Encoding currently
  selects one topic set deployment-wide, with an explicitly incompatible coordinated
  restart. There is no raw-to-Avro history conversion, cursor translation or automatic
  migration of session-keyed SQL exporter progress. Trigger: a deployment requires
  preserving existing session replay and cursor continuity across encoding changes
  rather than starting fresh sessions.
- **Per-kind typed payload schemas and schema references.** The envelope keeps payload
  bytes opaque and supports inline schemas. Trigger: a concrete consumer requires
  typed payload field evolution or reusable external schema dependencies.
- **OAuth token acquisition for Schema Registry.** Authentication uses explicit Basic
  credentials or mTLS. Trigger: a deployment requires automated OAuth client-credentials
  acquisition/refresh rather than externally managed credentials.
- **External cross-session topic discovery and aggregation.** Analytics consumer
  discovery and aggregation are deployment-owned rather than supplied by the envelope
  codec. Trigger: production analytics requires managed lifecycle and unified querying
  across dynamically created session topics.

## Anthropic surface not implemented

Operations Anthropic publishes that the registry does not serve. Classified `not-implemented` in
[`conformance-matrix.md`](./conformance-matrix.md), which is generated by `pnpm conformance:gen` —
this section is the reference all four of those rules point at.

| Family                        | Ops | Why not                                                                                                                                                    |
| ----------------------------- | --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/v1/tunnels`                 | 10  | Tunnels expose a sandbox port to the public internet. Orca's egress model routes outbound traffic through the MCP gateway; inbound exposure is undesigned. |
| `/v1/dreams`                  | 5   | Background "dream" runs are outside the current surface.                                                                                                   |
| `/v1/user_profiles`           | 5   | End-user profiles and enrollment URLs have no counterpart in the workspace identity model.                                                                 |
| `/v1/environments/{id}/work*` | 8   | The self-hosted work queue — a pull-based runner protocol. Related to the transport question below.                                                        |

`/v1/deployments` and `/v1/deployment_runs` (10 operations) are not served either, but they are not
work to do: the register classifies them `accepted-deviation`, because cron scheduling is the
Orca-owned `/v1/triggers` resource ([`cron-triggers.md`](./cron-triggers.md#decision)).

## Environment work stats: path and shape

`GET /v1/environments/{id}/work_stats` is served today and returns
`{ depth, in_flight, worker_connected }`. Anthropic publishes the same capability at
`GET /v1/environments/{environment_id}/work/stats`, returning `BetaSelfHostedWorkQueueStats`:
`depth`, `oldest_queued_at`, `pending`, `type`, `workers_polling`, all five required. The paths
differ by one separator, and the bodies overlap in exactly one field name whose two definitions do
not agree — Anthropic's `depth` is consumer-group lag on a Redis stream, ours is a `COUNT(*)` of
pending sessions with no runner minted.

Because the paths differ, the conformance differ classifies our route as an `extension` rather than
as a divergent `core` operation. It is recorded `fix-later` in
`services/registry-service-ts/conformance-decisions.yaml` (`extension-environment-work-stats`), not
`keep`: recording a shadow of a published operation as an accepted extension is what hard rule 2
forbids. [`orca-extensions.md`](./orca-extensions.md#environment-work-stats) carries the full
field-by-field comparison.

Aligning means renaming the route to `work/stats` and answering Anthropic's five fields. That is a
product decision, not a mechanical one: it breaks any client already reading `work_stats`, and
`oldest_queued_at` / `pending` / `workers_polling` need counting semantics this service does not
track. It also moves the row from `extension` to `core` and drops one operation from the
`missing-self-hosted-work-queue` family, so that entry's `covers: 8` becomes `covers: 7` — the gate
reports a stale count as `miscounted`, so the two must change in the same commit.

**Trigger:** the first external consumer of environment work-queue stats — an operator dashboard or
a self-hosted worker autoscaler — or any decision to implement the rest of the
`/v1/environments/{id}/work*` family above, whichever comes first. Building that family makes the
path question unavoidable, because its sibling routes land under `work/` either way.

## First-party clients on `/v1`

The engine serves its core API at `/v1/*` and extension groups at `/apis/<group>/<version>/*`; it
does not serve the `/v1/registry/*` prefix ([why](./api-groups-and-extensions.md#deprecating-v1registry)).
A first-party client generated against `/v1/registry/*` moves to `/v1` for core operations and to
`/apis/<group>/<version>` for extension groups, dropping `/v1/registry/*` in the same change: a direct
cutover rather than a staged migration, so no deployment serves two path dialects. Until a client has
moved, `GET /apis` and `GET /api` let it detect what a deployment serves instead of guessing from 404s.
**Trigger:** a first-party client release that must run against a self-hosted deployment.

## Production hardening

Operational work the engine needs before it can carry production traffic under an SLO.

- **In-use Vault deletion protection.** Vault DELETE currently revokes credentials even
  when an undeleted Session references the Vault; it has no `409 conflict_error` guard.
  An in-use check is deferred because it changes the existing credential-revocation
  contract, while soft deletion only changes metadata retention. **Trigger:** a caller
  requires Vault deletion to preserve access for existing Sessions. Define which Session
  states block deletion and how operators explicitly revoke access, then serialize the
  check with Session creation's shared Vault lock and update the API contract and tests.
- **Separate MCP large-result file access.** SDK spill files remain on the harness
  host, outside the sandbox tool filesystem. The hook bridge is blocked on trusted
  call-to-file attribution: a probe against SDK 0.3.220 accepted a legacy
  `{ toolResult: observedNotice }` response from the same remote tool that replays
  a previously observed same-session spill notice, producing the same
  primitive-string hook input as the original call. The
  retained `claude-sdk-tool-result-provenance.spec.ts` probe demonstrates this for
  fresh and SessionStore-resumed queries; a registered config root, tool name,
  filename, or hook string shape is not sufficient authorization. The fixture
  explicitly shares the original notice with the replaying server; it does not
  demonstrate discovery or synthesis of an unobserved host path. This is an SDK
  protocol characterization, not a claim that the production gateway accepts
  every response shape in the probe. Bounded agent Read pages reduce recursive
  spill risk but do not make remote MCP spill files accessible. No host-read
  fallback, result publisher, or reserved result root is enabled.
  **Trigger:** establish a trusted per-call artifact binding in the pinned SDK
  integration, or explicitly approve a different interception/trust boundary.
  Before publication is enabled, also verify exclusive atomic rename and hidden
  staging on each supported runtime. Local SRT requires narrow read grants: a
  broad parent `allowRead` overrides a staging `denyRead`; read-only is not hidden.
  Any approved bridge must also meet these acceptance constraints:
  - Expose only fixed-root publication, preserve agent/subagent permissions,
    and authorize the opened source file for the current query and call. Apply
    guardrails to recovered full content before making any copy agent-readable;
    denied or SDK-truncated content must not be presented as a complete result.
  - Reserve result/staging roots against overlapping resource mounts, exclude
    them from downloadable outputs, and enforce bounded, verified, no-clobber
    publication. Never grant arbitrary host/sandbox access or export payloads
    and credentials through telemetry.
  - Coordinate state evaluation through persistence acknowledgment; deduplicate
    policy updates and public results independently while preserving call IDs
    and upstream errors. Fence cancellation/teardown against late publication.
    Fail with a bounded unavailable result or abort, not an incomplete reference,
    host-path fallback, or re-execution of a stateful MCP call.
- **Session-runner Claude Read budgeting.** The independent Claude MCP Read tool
  in `services/session-runner/src/harness/claude/mcp-tools.ts` reads the entire
  file through `sandbox.files.read()` and then truncates text at 100000 JavaScript
  string code units. It does not use harness-server's byte-paged Read budget.
  **Trigger:** a session-runner Claude workload encounters oversized Read output
  or whole-file buffering pressure. Address that provider's paging, serialized
  output budget, and wire tests separately; do not assume the harness-server
  change covers it.
- **MCP JWT renewal within a running query.** Separate Claude harness queries check JWT
  freshness before startup, but a query lasting beyond the JWT lifetime can still lose MCP
  authentication. Runtime header replacement is deferred: an SDK 0.3.220 protocol
  probe (`claude-sdk-mcp-auth-rotation.spec.ts`) demonstrated that changing Authorization
  reinitializes the remote MCP session and loses its server-side context. No query-duration
  cap, auth relay, or in-process remote MCP bridge is included in the startup-refresh fix.
  **Trigger:** select and validate a request-time authentication strategy that preserves
  MCP session/context and in-flight calls, including cancellation, tool discovery, and
  result fidelity. Self-hosted runner credential delivery needs its own renewal path.
- **LLM gateway JWT renewal within a running query.** Gateway-selected `separate`
  Sessions refresh the model JWT before each Claude SDK query, but the SDK
  subprocess keeps that token for the query's lifetime. The Registry's
  `SESSION_JWT_TTL_SECS` defaults to 300 seconds; a query that continues beyond
  the JWT expiry can receive a Gateway 401 on a later model request.
  **Trigger:** a long-running gateway-selected query hits token expiry. Add a
  request-time auth mechanism and verify streaming, cancellation, and usage
  delivery across refreshes.
- **Per-operation RBAC.** Authorization is workspace-level everywhere except Triggers: a credential
  resolves to one workspace and may perform any other operation within it.
  `AuthenticatedPrincipal.scopes` is populated and workspace keys carry a single
  `workspace.full_access` (`registry-service-ts/src/api/admin.routes.ts:128`). Only the
  `/v1/triggers*` handlers inspect scopes, accepting `workspace.full_access` or the matching
  `workspace.agentTriggers.*` scope (`registry-service-ts/src/auth/workspace-scope.ts`). There are no
  per-resource permissions on other resources (for example create/alter/delete/describe on Agents),
  and no role model sits above them.
- **User-delegated workspace key management.** Only organization-admin credentials create or update
  workspace API keys; a workspace key cannot create or rotate itself or its siblings. The intended
  model is an OIDC workspace membership rather than a workload API key. **Trigger:** users who must
  manage their own workspace's keys without an organization-admin credential.
- **Distributed per-workspace rate limits.** The optional heavy-read admission gate bounds
  active and queued list reads per process/workspace. It does not provide cross-replica request
  rates, pre-auth cold-verification budgets or independent capacity for internal traffic.
  **Trigger:** measured mixed-load saturation after enabling and tuning the local gate.
- **SSE per-tenant limits or producer-side backpressure.** Each event stream has its own bounded
  buffer; a client that falls behind is dropped with `client-too-slow` and resumes from its last
  event ID (see [`sse-backpressure.md`](../operation/sse-backpressure.md)). Nothing limits streams
  per tenant, and the producer receives no backpressure signal. **Trigger:**
  `registry_service_sse_drop_total{reason="client-too-slow"}` above about 1% of stream starts.
  Raise `SSE_BUFFER_SIZE` first; if drops persist, add per-tenant limits or a producer-side
  backpressure protocol.
- **harness-server on the shared sandbox packages.** session-runner and Registry use
  `@orca/sandbox-runtime`, and Registry's cloud Environment launchers use `@orca/cloud-sandbox`.
  harness-server imports only `composeSkillsCatalog` from them: it keeps its own sandbox runtimes
  (including E2B and OpenSandbox) and write-policy code under `src/sandbox/`, and its own copy of
  the Skill-bundle validators, so a fix to shared behavior has to be made in both copies.
  **Trigger:** the copies diverging in behavior, or a runtime change that has to land in both. Move
  harness-server onto the packages and delete its copies.
- **Memory-version retention of any kind.** Versions accumulate indefinitely: `memory_versions`
  has no expiry column, `LocalMemoryStore` never prunes, no migration adds a policy, and no bucket
  lifecycle rule ships in the chart. Per-workspace configuration is the eventual goal, but the
  present gap is that nothing expires at all. Kafka tier-offload stays the broker operator's
  responsibility.
- **Archived-workspace data garbage collection.** Archiving a workspace deletes none of its File or
  Memory bytes or metadata; they remain for retention and forensics, and no SQL cascade reaches them
  (File and Memory metadata live in separate databases). **Trigger:** a retention requirement for
  archived workspaces' data. Define an explicit, asynchronous garbage-collection policy rather than a
  synchronous SQL cascade.
- **Audit dashboards.** The ai-gateway emits one audit record per `/v1/mcp` call to Kafka; nothing
  consumes it into a dashboard.
- **Per-workspace OIDC issuers.** `OIDC_ALLOWED_ISSUERS` is a deployment-global env list
  (read in `registry-service-ts/src/config.ts`); there is no per-workspace issuer column.
- **Crash-recovery and tiered-offload E2E coverage.** No suite kills and restarts
  `harness-server` mid-turn, and none forces a tiered-storage offload before re-reading old
  offsets. `crash-recovery.spec.ts` appends its event before any dispatcher exists and then
  constructs one, so it covers cold-start catch-up — not redelivery after a stop, which would
  need a second dispatcher, a rebalance, and an uncommitted offset.
- **Trigger fire-row retention.** Nothing prunes terminal fire rows: `agent_trigger_fires` has no
  expiry column, no code path deletes or expires a row, and rows are retained even when the Trigger
  is archived. The public-history policy that would govern it is undecided, and the same decision
  gates widening the Trigger `source` union — adding Kafka or Pulsar needs an answer for how that
  runtime model backs `/v1/triggers` without a competing wire contract.
- **A machine check for floating promises.** `eslint.config.mjs` extends
  `tseslint.configs.recommended`, not `recommendedTypeChecked`, so `no-floating-promises` and
  `no-misused-promises` never run — CI cannot see that class of defect anywhere in the workspace.
  It is a crash class, not a style one: `@orca/session-runner`'s `start` script is a bare
  `node dist/main.js` and it installs no `unhandledRejection` handler, so Node's default
  throw-mode turns one rejected un-awaited promise into process death. Two `void`ed calls in
  `services/session-runner/src/tunnel/serve.ts` (`handleTunnelFrame`'s pong send and
  `receiveOrAbort`) did exactly that; both were found by reading, and the guard today is
  convention — a deliberately un-awaited call carries a `void` prefix plus a comment saying why it
  cannot reject. Trigger: the next floating-promise defect that reaches a session, or
  a CI budget that can absorb the type-aware pass, which needs a `projectService` and so turns
  `pnpm -r lint` from a syntax-only walk into a full type-check of every package.
- **Runbooks** for the managed-agents components.
- **Production container hardening.** The service Dockerfiles are the original scaffold.

## Remaining API performance work

Current batching, auth proof reuse, admission and metrics are documented in
[Registry](services/registry-service.md#api-read-performance-and-admission).

- **Mixed-load deployment validation and deeper tracing.** Pool/region experiments, request
  TTFB, handler/projection/serialization spans, OIDC and external-I/O spans, and telemetry overhead
  measurements remain. **Trigger:** a controlled deployment with the same request mix and all
  active pools recorded; do not infer production p95 from local query budgets.
- **End-to-end cancellation and caller polling.** Queued admission and not-yet-started read chunks
  stop on disconnect; already-submitted SQL and provider calls lack a shared request deadline.
  **Trigger:** driver-safe cancellation/late-checkout-release tests and identified polling owners.
  Any coalescing of `lastUsedAt` also needs an agreed timestamp/audit freshness contract.
- **Memory logical pagination and version summaries.** Page-ID filtering reduces unrelated
  histories, but namespace enumeration and unrestricted version lists still scan their scope.
  **Trigger:** an equivalent backend contract for depth-before-pagination, UTF-16 path order,
  timestamp ties, rename/delete/redaction semantics and existing offset cursors. Add first/latest
  summaries for long individual histories without fetching every version.
- **Outcome read model and revision-aware pricing reuse.** Outcome folds still read all matching
  history for the selected Sessions; pricing still resolves the current catalog without a TTL
  cache. **Trigger:** replay/backfill and dual-read parity for outcomes, durable revision/invalidation
  coverage for pricing, including organization precedence and unknown prices.
- **Shared SSE subscriptions and write-critical-path changes.** A bounded replay-to-live hub,
  outbox leases, object/archive packaging and cross-replica launch coordination remain separate
  changes. **Trigger:** three-backend replay/cursor/backpressure tests, crash and duplicate-publication
  recovery, bounded temporary resources, and multi-pod owner/launch recovery before replica scaling.

## Agent observability

Transcript envelopes support optional user attribution, and Registry stamps verified OIDC attribution
for client events. `@orca/agent-event-contract` supplies the pure canonical producer vocabulary,
ID/subpath helpers, and constrained lifecycle/model payload builders. Harness now uses the strict
lifecycle, acceptance-marker, and coarse model-summary builders. Both current Claude paths retain the
`span.model_request_start/end` kinds but label their one-pair-per-Harness-query/turn observations as
`turn_model_summary`; the start envelope is the sole start identity, and the end references it explicitly.
Registry keeps those Orca-only summary fields out of the default Anthropic view. Harness preserves valid
supplied envelope IDs and canonical subpaths into Transcript events. Both current Harness production paths
now complete every emitted event with a unique canonical ID and explicit primary subpath. The service-local
output type requires both fields, SessionRunner passes them directly, and public event conversion never
derives envelope identity from payload fields. Shared conformance now covers both current Claude producers
at primary-path/coarse-summary granularity. Child public subpaths, per-logical-call provider observations,
and full multiagent parity remain blocked on explicit producer evidence. Remaining delivery:

1. **Phase 1 — remaining canonical parity:** carry trustworthy child public subpaths through both current
   Harness paths. Per-logical-call provider observations remain blocked until a producer emits explicit
   cardinality and correlation evidence.
2. **Phase 2 — Registry control plane (started):** migration 0048 ships durable binding/version/
   credential-reference/settings/pin tables and atomic organization/workspace setting provisioning.
   The admin listener now has read-only organization/workspace state views with typed standalone
   contracts, repeatable authoritative precedence resolution, non-secret binding metadata, scoped
   `observability:read`, and opaque strong ETags. New public and Trigger-created Sessions atomically
   select and pin active or disabled observability state with observed epochs, effective capture mode,
   and Agent-version Harness snapshot. Session archive/delete atomically tombstone that exact pin and
   advance its Session revocation epoch; pin archive is idempotent, while delete retains the pin after the
   Session is soft-deleted. Migration 0049 backfills every missing pin from the post-0048 / pre-pinning writer
   window with safe disabled state and adds a temporary `sessions` fallback trigger; its conflict-do-nothing
   insert preserves authoritative active/custom pins from current writers. Migration 0054 temporarily
   backfills archive/delete lifecycle mismatches and enforces Session pin tombstones in a `sessions` trigger,
   including workspace-archive fan-out, while old direct lifecycle writers can coexist with the application
   helper. Migration 0055 adds the DB-only fenced mutation persistence kernel: append-only target
   reservations, generation/owner CAS, durable writer-leased credential staging tombstones with proposed
   credential-head identity, opaque versioned bundle helpers, same-binding superseded-secret cleanup claims,
   TTL/rebindable organization-admin idempotency, transaction-scoped authoritative state cache records, and
   atomic audit finalization with post-apply credential-head proof. The organization admin listener now uses it
   for fenced `PUT /v1/organizations/agent_observability`: strict `otlp_http` default creation/target replacement,
   same-target immutable policy versions, SecretStore staging, authoritative response caching, and non-overlapping
   retention/staging/superseded-secret maintenance. The organization admin listener also rotates only the
   current active organization-owned `otlp_http` credential head through the same fenced lifecycle: strict
   credentials-only body, exact state ETag, binding-target idempotency replay across later default replacement,
   head CAS, and asynchronous superseded-ref cleanup. The admin listener also disables an organization default
   through route-scoped replay, optional `If-Match`, exact setting/current-binding reservation preemption,
   same-transaction finalization, default-revocation epoch advance, and draining only an active old binding;
   it safely clears a selected non-active or credential-head-missing default without altering workspace custom
   state or deleting credentials. Workspace archive now locks its setting authority and advances its
   workspace revocation epoch atomically with workspace, API-key, Session, outbox, and audit rows. Migration
   0056 backfills durable archive markers and temporarily enforces that workspace marker fence for direct old writers.
   Binding-wide lifecycle and exporter process/OTLP surfaces remain. After all
   pre-pinning Registry writers are retired, a
   follow-up migration removes trigger `agent_observability_sessions_provision_legacy_pin` and function
   `agent_observability_provision_legacy_session_pin`; the separate 0048 parent-provisioning triggers remain
   until all pre-0048 writers retire. A separate follow-up removes trigger
   `agent_observability_sessions_enforce_lifecycle` and function
   `agent_observability_enforce_session_pin_lifecycle` only after every direct Session archive/delete writer,
   including workspace archive fan-out, calls the application lifecycle helper and all older replicas have
   retired. A separate follow-up removes trigger
   `agent_observability_workspaces_enforce_archive_revocation` and function
   `agent_observability_enforce_workspace_archive_revocation` only after every direct Workspace archive writer
   records its archive marker and advances its setting before Workspace status and all older replicas have retired.
   A separate low-lock maintenance migration validates 0056's initially
   `NOT VALID` archive-marker ownership FKs after the rollout; 0056's
   backfill and trigger already validate every existing marker, and the FKs
   enforce every marker written after they are added. Organization and workspace mutations
   reject the Langfuse semantic profile when the target has no external project identity.
   Staging-tombstone retention remains intentionally unbounded: current
   SecretStore writes have no hard cancellation or verified-quiescence contract. Add bounded tombstone
   pruning only after a backend supplies one of those guarantees, then prove a late put cannot recreate a
   deleted ref.
3. **Phase 3 — exporter + OTLP (Kafka broker-native default):**
   `@orca/observability-exporter` defaults to Kafka state without an exporter Postgres connection.
   It consumes authoritative Session records directly, writing incremental identity/acceptance keys,
   a v2 head, canonical delivery records and source offsets in a Kafka transaction; there is no
   second Transcript read. Large reducer/delivery JSON uses authenticated blob chunks in the existing
   checkpoint topic. A shared read-committed reader rebuilds a fresh worker-thread SQLite index,
   with bounded point lookups and derived ledger counts rather than repeated per-Session log scans.
   Quiesced v1 checkpoints up to 512 KiB import in one transaction without changing their offsets,
   pinned suppression or delivery backlog. Source join and lazy restore admission are independently
   bounded; readiness retains its initial-discovery/runtime/Admin contract. Startup bootstraps
   or validates internal topics, and the process discovers Session topics periodically. Delivery uses
   read-committed records, fresh audited Registry credentials, and Langfuse-profile OTLP HTTP/JSON
   over hardened public HTTPS — metadata only, plus bounded turn and tool content when Registry
   authorizes `raw_io` capture. External HTTP delivery is at-least-once, not atomic with
   Kafka offset commit. Retries pause a delivery partition; attempt counts and delay timers reset
   on restart. Compacted per-partition delivery progress is committed with delivery offsets and
   restores expired/deleted group positions without resending acknowledged history. Identity/state
   failures stop the instance rather than durably quarantining one Session.
   The [exporter README](../../services/observability-exporter/README.md) documents topic/group/
   transaction/restore ACLs, retention constraints, and restore/checkpoint limits.

   Explicit `OBSERVABILITY_EXPORTER_STATE_BACKEND=postgres` retains the legacy inbox/replay,
   fenced SQL state/outbox, durable attempt scheduling, binding cooldowns and terminal outcome rows.
   A DSN without an explicit backend fails startup; Kafka does not import SQL progress. Existing SQL
   integration tests and the opt-in `test:smoke:litefuse-vertical` remain legacy-path evidence, not
   broker-native recovery or Helm rollout proof. The direct Litefuse smoke exercises the shared
   projector/client only. Neither smoke is a GA-readiness claim.

   Remaining work, with triggers:
   - **Exporter v2 capacity and rollout evidence:** an earlier checkpoint design could exhaust the
     512 KiB checkpoint limit through a suppressed Session identity ledger, and a deployment with
     several hundred Session topics exposed serial consumer admission and repeated shared-log
     restore costs. The v2 runtime addresses the growing-head and repeated-scan paths; validate
     several-hundred- to 1000-topic and million-identity Kafka replay workloads under 1 CPU/1 GiB
     budgets, SIGKILL/network commit uncertainty, forced compaction and a production-compatible
     Kafka endpoint before
     claiming deployment-scale recovery or a startup SLO. Verify Linux amd64 and native source-build
     fallback in addition to local Node 22/Linux arm64 checks before widening image support claims.
     A local Node 22 SQLite/production-projector check loaded one million identities with a
     297-byte head and about 150 MiB peak process RSS using a 4 GiB scratch budget; that isolated
     index/lookup evidence does not establish Kafka replay throughput or the target container SLO.
     Pre-implementation ablation experiments separating real reducer, local Kafka protocol and
     SQLite-model results are not substitutes for runtime integration and deployment evidence.
     Fixed multi-topic groups/custom assignment and source-group migration are outside this first
     increment; reconsider them only if full-scale measurements still show topic-count pressure.
     Warm local-index adoption, application caches, incremental family paging and historical-view
     machinery require measured cold-replay/query/write-amplification or consistency needs before
     being added. Larger-than-supported v1 imports require a separate migration capacity decision,
     not an automatic fallback to multi-transaction staging. Stronger restored-readiness semantics
     require an explicit operations contract and empty-topic/standby initialization evidence.
     Preserve source offsets, pinned suppression, delivery backlog and exact replay/conflict
     detection; do not substitute offset resets, ledger eviction or an encoding cutover.
   - **Durable Kafka retry bookkeeping:** persist attempts/deadlines and delivery outcome diagnostics
     when restart-stable backoff or operator audit requirements exceed compacted delivery progress.
     Current ephemeral partition pauses are not durable scheduling or a binding-wide cooldown.
   - **Advanced scheduling and failure isolation:** tenant fairness, binding-aware concurrency,
     circuit breaking, bounded topic reconciliation, and durable quarantine/DLQ when sustained
     test-deployment traffic demonstrates hot-partition blocking, topic-count pressure, or one bad Session affecting
     unrelated work. Establish explicit ordering and retry/requeue contracts before adding them.
   - **Automated SQL cutover and operator requeue:** build migration/import and controlled requeue
     tooling when an existing SQL installation needs to move to broker-native state or operators
     need replay. Require source/checkpoint/delivery reconciliation and deterministic-identity evidence;
     changing backend/group IDs or rereading source into a second projection path is not migration.
   - **Safe retention and Session lifetime policy:** delivery currently requires unlimited time/byte
     retention, state identities are not evicted, and each fresh process scans the shared log into
     its bounded scratch disk index. Abruptly terminated containers can leave unused scratch
     directories until Pod recreation; add safe stale-directory reclamation if crash/restart
     testing demonstrates disk pressure, without adopting stale state or deleting another live index.
     Add acknowledged-delivery cleanup, source-retention coordination, identity lifetime bounds and
     scalable restore when storage growth or Session/log size approaches current limits, before
     claiming production-scale retention. Prove recovery after expiry and compaction before relaxing
     the required topic policies; cleanup must not silently discard unacknowledged delivery or identities.
     The redacted-I/O requirement establishes finite retention on the existing delivery
     topic as the preferred design, not a new content topic. Before enabling it, implement bounded
     retry age, audited delivery-retention-gap recovery, checkpoint/chunk and local-index cleanup,
     and non-resurrection on restore. Expired delivery may be lost; active recovery state must not
     be expired by applying the same TTL blindly to the compacted checkpoint topic.
   - **Recovery and production rollout evidence:** broker-native crash/rebalance/fencing, ambiguous
     commit, retention-loss and restore-limit tests plus Helm rollout coverage before production use.
     SQL smoke results do not establish these guarantees.
   - **Producer parity:** primary-path metadata-only local/MCP/custom tools and separated-Harness
     evaluator observations are supported. Full multiagent tool traces remain blocked on canonical
     child subpath/identity conformance, including reused native IDs across threads; no payload-derived
     hierarchy substitutes for that evidence. In-sandbox evaluator parity requires the same explicit
     identity/correlation/result contract and producer conformance. Evaluator model-call enrichment
     requires actual per-call identity/usage evidence, not placeholder zero usage or explanation text.
   - **Raw I/O rollout and deeper Litefuse integration:** current capture, attribution, approval
     and migration behavior is documented in the
     [exporter README](../../services/observability-exporter/README.md) and
     [Registry service](services/registry-service.md). Remaining work, data usability first:
     - Validate raw I/O, native attribution, approval, status and usage through the deployed
       Litefuse read-back/UI once an authorized test project and credentials are available.
     - Enable capture only with explicit operator authority and a reviewed test scope. Prefer an
       isolated Registry/database; a global ceiling change can affect other eligible new Session
       pins. Use the [platform policy administration API](workspace-administration.md#platform-observability-policy)
       for authorized ceiling changes; scoped ceilings and binding requests remain separate.
     - Add finite retention and cleanup before production expansion; synthetic validation need
       not wait for it, while real-content trials require acknowledgement of the current boundary.
     - Add true model-call/TTFT data only with producer identity/timing evidence. Add thin Scores
       integration when trusted results need exporting; keep grader failures distinct from task
       failures. Prefer Litefuse-native datasets/experiments/annotations or external SDK scripts.
     - Extend retrieval/memory/subagent/media fields for concrete debugging or evaluation gaps.
       Revisit automatic redaction only with an explicit capture policy, corpus and acceptance
       requirement. Do not introduce policy engines, capture leases, send-intent frameworks or
       new content/eval platforms merely to support these integrations.
   - **Additional targets/protocols:** generic target/protocol variants remain deferred until a
     validated tenant requirement and corresponding privacy/egress acceptance evidence exist.

4. **Phase 4 — demand-gated Langfuse SDK:** add isolated SDK client generations only for a validated
   tenant requirement beyond OTLP.
5. **Phase 5 — operations:** the image release path and the default-disabled Helm workload include
   dedicated identity and basic health probes. Production rollout coverage, dashboards, alerts,
   retention, and operator requeue remain deferred until sustained test-deployment traffic and failure-mode
   validation establish operational requirements.

Two producer gaps sit outside that plan, both created by `@orca/session-runner` landing as a
third event producer:

- **The runner does not consume `@orca/agent-event-contract`.** It is a separate process that
  re-declares the kind strings and subpath constants it speaks
  (`services/session-runner/src/harness/multiagent/thread-events.ts`), and it completes neither
  half of the canonical envelope: its wire line omits `id` unless the harness had a stable one,
  and omits `subpath` for a primary-thread event. The registry's bridge mints the missing
  identity. Producer-supplied identity is what lets a re-push after a recovery replay or a tunnel
  reconnect deduplicate, so an event emitted without one cannot be. A unit pin
  (`services/session-runner/test/unit/multiagent-thread-events.spec.ts`) reads the contract source
  and asserts the re-declared constants against it, so the two copies cannot drift silently.
  Trigger: duplicate events observed after a reconnect or replay, or a second consumer of the
  runner's stream that needs producer-supplied identity.
- **Shared harness conformance does not reach the runner's producers.**
  `services/harness-server/test/support/model-summary.ts` is imported by harness-server specs
  only, so the envelope and coarse-summary checks cover its two Claude producers and nothing else.
  The runner's own gate asserts turn-terminal delivery across its ten providers, not envelope
  shape. Trigger: the runner adopting the contract above, which is what would make the envelope
  and model-summary assertions meaningful there.

## Real-provider e2e for native-CLI providers

The session-runner's native-CLI providers (`claude-code`, `codex`, `cursor`, `pi`) and the generic
`custom` provider have no end-to-end suite that boots a real vendor binary with a real credential;
their specs use fake CLIs, and CI's real-model coverage is the SDK harnesses in `e2e-stack.yml`
Layer B. The intended shape is a local-only, self-skipping matrix: one case per provider, each gated
on its binary being on `PATH` and its credential being set, driving a real turn through
`client → registry → worker → session-runner → native CLI → bridge → SSE`, with credentials
forwarded through `ORCA_RUNNER_ENV_PASSTHROUGH`. **Trigger:** a native-CLI provider regression the
fake-CLI specs did not catch, or a vendor CLI release that changes its stdio protocol.

## Deferred by design

- **Retain sandbox handles across idle.** harness-server currently destroys and
  rebuilds idle sandboxes. Trigger: a runtime checkpoint/attach contract that
  preserves scratch state and passes reconnect, cleanup and ownership tests.
- **Persistent Claude on cloud separate deployments.** The persistent provider
  exists in session-runner, while harness-server registers the ordinary Claude
  SDK provider only. A cloud separate request for the persistent identity fails
  setup explicitly. Trigger: demand for persistent Claude on this deployment
  path; add a real provider and lifecycle conformance coverage before advertising it.
- **DeepAgents SDK integration.** This adapter is separate from the
  existing Pi SDK, Pi CLI provider and Codex SDK. Trigger: an approved SDK-specific scope;
  integrate with the shared catalog, ownership rule and runner contract tests,
  preserving immutable Agent harness identity and native model policy.
- **Further guardrail kinds.** Each is additive — new catalog entries and at most one new
  interface, with no change to the guardrail model, the engine or the API shape. Model-judged
  guardrails (intent authorization, task-switch detection, prompt-defined policies) need a judge
  client, a model-selection decision and `ask` at `request`; risk scoring needs a
  data-classification label vocabulary and conditional firing; sandbox configuration enforcement
  needs a rule kind that overrides configuration rather than returning a verdict. Trigger: a
  policy requirement that the builtin catalog and CEL expressions cannot express.
- **Anthropic Skill references.** A `type: "anthropic"` Skill reference resolves only to a locally
  stored immutable bundle, and nothing maps Anthropic-published Skills to one, so Session creation
  rejects it ([`skills.md`](./skills.md#session-pinning)). Building it means an operator catalog that
  stores those bundles and maps each reference to one. Trigger: an Agent that must reference
  Anthropic-published Skills.
- **SPIFFE/SPIRE workload identity for internal traffic.** In Kubernetes, Registry verifies each
  internal caller's projected ServiceAccount token with a `TokenReview` against one Kubernetes API
  server, so per-workload identity covers only callers whose tokens that cluster issues; outside
  Kubernetes every internal caller shares one service token (see
  [`internal-traffic-auth.md`](../operation/internal-traffic-auth.md)). Trigger: an internal caller
  that must run in a different cluster from Registry and still needs its own workload identity.
  Replace TokenReview with SPIFFE/SPIRE-issued identities for that case.

Decided against for now, each with the condition that would reopen it.

### Sketch: `SyncMemoryFuseStrategy`

A custom libfuse daemon (packaged into the `orca-default` E2B template alongside `s3fs-fuse`) that
calls the scoped internal `memory-versions` route synchronously on every `write` syscall before
returning success to the agent. The polling watcher stays as a backup: if a sync write loses a
network round-trip but the daemon still reaches S3, the watcher catches up on the next tick.

The public SDK contract would not change — registry routes, resource shape, and version chain stay
identical. The only user-visible difference is that the consistency-window caveat in
[`memory-conflict-semantics.md`](./memory-conflict-semantics.md) goes away.

## Designed, not built

**The `llm_request` interception point.** Registry serves the guardrail API
group and Harness evaluates `request`, `tool_call` and `tool_result`, but no
topology evaluates `llm_request`: nothing hands a guardrail the serialized
outbound request. `deny_pii_in_llm_request` therefore screens only its
`request` leg, which is a preview of the turn rather than the bytes that reach
the model — it cannot see PII a tool result introduces mid-turn. Both harnesses
surface the gap instead of hiding it (`separate` warns and keeps the enforceable
legs; `in_sandbox` refuses to start), and authoring rejects an explicit request
for the phase, so nothing is silently inert in the meantime.

Building it means pointing the SDK's configurable base URL at a harness-local
model-endpoint interceptor that evaluates the stateless pass on the exact bytes
it forwards, then forwards on allow or fails the call with the guardrail's
reason on deny. It needs no SDK hook surface — the SDK owns serialization and
compaction and exposes no pre-model hook — because the harness owns the model
endpoint, and a request the SDK mutates after evaluation cannot reach the model:
the evaluated bytes and the forwarded bytes are the same bytes. Under `separate`
that interceptor is in-process with `harness-server`; `in_sandbox` additionally
needs its protocol to carry the interceptor and interpose on the sandboxed SDK's
path to the configured gateway URL. Its verification replaces the colocated
startup-rejection regression with a model call made inside the sandbox with the
PII present only in a tool result — pinning full-prompt evaluation — plus
fail-closed evaluator errors and metadata-only persisted evaluation records.
Trigger: a guardrail that must screen model input rather than user input —
which is every real deployment of the PII screen.

Two phases have no enforcement point at all. `response` and `llm_response` are
modelled and reachable through the type system, but nothing fires them and no
builtin declares them, so authoring rejects them outright rather than storing a
rule that could never evaluate. They stay modelled because the failure-mode
table is defined over all six phases; wiring either one needs a use case first.

**Request-phase budget approval.** `request` has no confirmation exchange.
Default unpriced handling allows the first pending acknowledgment and denies a
later unapproved request; soft monetary thresholds ask only at `tool_call`.
Trigger: a text-only client needs to approve continued spending or unmetered
usage directly at the request boundary. Add a request approval protocol and
end-to-end confirmation coverage together.

**Deterministic spend on Kafka and Pulsar.** The owned spend suite uses Postgres
transcripts; the paid agent matrix covers Kafka, Postgres and Pulsar. Trigger:
backend-specific usage delivery or restart behavior changes. Extend owned
infrastructure and cleanup to broker-backed transcripts, then repeat ACK-loss,
restart and subagent accounting scenarios on those backends.

**Scheduled model-price seed refresh.** `packages/harness-catalog/src/model-prices.seed.json` is
updated by hand; the 180-day staleness test in `@orca/harness-catalog` is the only check on its age.
The designed job fetches a machine-readable upstream catalog, regenerates the seed through
`parseModelPriceCatalog` (the parser the Registry refresher uses) and opens a pull request only when
the content differs, so a human reviews an actual price diff and nothing merges automatically.
Trigger: the staleness test fails, or a published price change ships in a release before the seed
carries it.

**Promoting an extension group to core.** When Claude's API adds a capability an `/apis/*`
extension group serves, the designed procedure is: core implements the Claude-compatible endpoint
under `/v1`; the extension path stays as a deprecated alias for at least one release cycle; and the
extension's discovery entry is marked deprecated before removal. None of it is built: no extension
has been promoted, nothing serves an extension path as an alias, and `ApiGroupList` has no
deprecation field. Trigger: Claude's API adding a capability that an `/apis/*` group serves. Add the
discovery deprecation field in the same change as the first alias. See
[`api-groups-and-extensions.md`](./api-groups-and-extensions.md#promotion-path).

**Registry-backed Gateway guardrail rollout.** Registry serves Session-scoped bundles and the
Gateway chart has an opt-in Registry source, but the deployed Gateway image and live end-to-end
path have not yet been validated together. Trigger: deploy an image with RegistryGuardrailSource,
enable the chart switch, then verify policy refresh, coordinator and delegated Agent requests,
and cost and token budget enforcement against Registry state before enabling it by default.

**Guardrail `tool_call` and `tool_result` on `session-runner`.** The runner
carries its Registry-composed guardrails and evaluates stateless, top-level
`request` before the model sees a turn. It refuses every other phase at snapshot
apply. A `tool_call` or `tool_result` rule is therefore visibly unsupported,
never accepted as inert policy.

Both have real enforcement points already. `tool_call` belongs at
`ToolPermissionResolver.policyFor()` (`harness/agent-harness.ts`), the one seam
every provider but `mock` consults immediately before parking a call, with the tool
input already in scope; widening it to a three-valued decision keeps the session
loop free of provider branching and needs no provider to import the engine.
That widening also has to close a pre-existing gap: the runner's
`ToolPermissionPolicy` is two-valued, so an `always_deny` from the registry is
silently dropped today. `tool_result` belongs at the single point where every
provider's events are encoded onto the turn stream. Trigger: either is worth
building the moment the runner serves traffic.

The same increment must carry the dispatched subagent identity into evaluation.
The composed fold already labels subagent-specific rules, but the top-level
request event has no dispatched subagent yet; accepting those rules now would
filter them out forever. The runner therefore refuses subagent-scoped policy
until the coordinator evaluates it at dispatch and at the later per-subagent
phases.

**Durable guardrail state on `session-runner`.** Registry restores state in the
snapshot. Managed Codex SDK and Pi SDK request policies already use Registry-owned durable
preflight and SDK usage accounting. Other providers and later phases refuse stateful rules until mutations have an
acknowledged durable path back. The Registry state-update endpoint already has
atomic set/increment/append/delete semantics; the missing piece is a scoped
runner-to-owner-pod protocol that authenticates the session, forwards a batch,
waits for Registry's acknowledgement, and blocks the guarded action on failure.
The turn's NDJSON response could carry advisory updates, but it cannot
synchronously acknowledge a write before releasing the action, so it is not
sufficient for fail-closed enforcement. `subject_window` usage remains
Registry-derived. Trigger: a stateful guardrail whose counter must survive a
respawn.

**Self-hosted runner transport.** Both halves are built. Registry serves the runner tunnel
`WS /v1/tunnels/runners/:runnerId` (`services/registry-service-ts/src/api/runner-tunnel.routes.ts`)
and the Environment worker tunnel `WS /v1/tunnels/environments/:environmentId`
(`worker-tunnel.routes.ts`), both registered in `src/server.ts`: a WebSocket channel, binding-token
runner authentication that is loopback-only by default and fails closed on owner resolution, and
resolved-owner registration plus claim-based dispatch. `@orca/session-runner` dials the runner tunnel
and serves the pushed `/v1/runner/*` routes; `environment-worker` dials the worker tunnel and launches
runners — see [`services/session-runner.md`](./services/session-runner.md),
[`services/environment-worker.md`](./services/environment-worker.md) and
[`services/registry-service.md`](./services/registry-service.md) ("Runner tunnel").

Two conditions would reopen the design rather than just the implementation:

- **Partial-turn loss becomes user-visible.** The turn request and its agent-event stream are one
  tunneled streaming POST, so a mid-turn drop loses the un-streamed remainder. A turn that produced
  _no_ agent event self-heals on the next catch-up; a turn that dropped _after partial output_ is
  treated as answered and is not auto-resumed, because re-driving would duplicate the persisted
  prefix. If that proves visible in practice, split the unified POST into a submit plus a resumable
  per-turn stream, or persist a per-turn terminal marker so partial turns become re-drivable without
  duplication.
- **Resume replay gets expensive.** Resume replay walks the whole transcript to its current head and
  pushes every event after the runner's cursor, in acknowledged 500-event chunks; nothing caps the
  total. If very long transcripts make that costly, fold recovery into a durable per-runner offset
  the runner advances.

This is the same shape as the `/v1/environments/{id}/work*` family above; the two should stay in step.

## Known limitations

Present behavior a user or operator could be surprised by. These describe today's code — the
corresponding design docs state the same behavior without promising a fix.

**Sandbox and tools**

- Separate Codex recovery abandons unfinished turns explicitly and retains the
  previous native snapshot; it does not resume a process-local callback wait.
  Continuing an interrupted turn requires an SDK checkpoint at the tool/result
  boundary and an acknowledged result-consumption protocol. Trigger: a workload
  requiring an unfinished turn to continue after harness-server replacement.
- Colocated Codex callback waits are process-local. Reconnect explicitly closes an
  incomplete callback turn as `custom_tool_callback_abandoned`, even when the result
  was persisted before the drop. Durable callback continuation requires a resumable
  SDK tool-call checkpoint and an acknowledged result-consumption boundary. Trigger:
  a workload requiring callbacks to survive runner replacement without a new message.
- Codex callback results support inline text, text documents, search results, and
  base64 PNG/JPEG/WebP/GIF images. URL/File-store sources and binary documents such
  as PDF fail explicitly. Supporting them requires workspace-scoped File-store
  resolution, bounded URL fetching through approved egress, and an explicit binary
  document conversion contract. Trigger: a workload requiring those source formats.

- The separate Claude SDK runtime exposes custom tools only for the primary
  agent. Coordinator subagent snapshots do not carry `custom_tools`, so child
  agents cannot initiate the `agent.custom_tool_use` /
  `user.custom_tool_result` callback flow there.
- `web_fetch` in `agent_toolset` runs from the harness host and does **not** pass through
  ai-gateway, so it is outside the vault-aware egress path that covers MCP.
- The native `codex` harness is registered in `@orca/harness-catalog` and has an image tag, but
  `@orca/sandbox-harness`'s provider registry ships only the `claude`, `codex-sdk` and `pi-sdk`
  providers — selecting `agent=codex` fails with `unsupported agent: codex`.
- In the legacy `@orca/sandbox-harness` HTTP path, warm `claude_code` turns pass
  the SDK `session_id` as `resume`; the `codex` rollout equivalent is absent.
  Both managed `codex_sdk` modes support native checkpoint recovery; see
  [session-runner](services/session-runner.md) and [harness-server](services/harness-server.md).
- The `MemoryVersionWatcher` polls on a fixed 2 s interval. It is not operator-tunable; no env var
  is read for it.

**Storage**

- No anti-virus or content sanitization on file upload.
- One object-storage bucket and one KMS configuration per deployment. Per-workspace buckets and
  per-workspace keys are not supported; workspace isolation is enforced by key prefix.
- `GET /v1/files/{id}/content` is a plain HTTP body stream. There is no chunked or resumable
  transfer for large downloads.
- File `scope_id` is unvalidated on the public routes. The `mst_…` (memory-store attachment) and
  `agnt_…` (agent-pinned reference file) prefixes are reserved in the id space but nothing rejects
  them: `GET /v1/files?scope_id=mst_…` answers `200` with an empty page, and `POST /v1/files`
  hard-codes `scope_id: null`. See [`output-capture.md`](./output-capture.md).

**API and auth**

- No `/v1/api_keys` route. Workspace API keys are provisioned through the admin listener's
  `/v1/organizations/*` routes.
- Environment list filters are incomplete. Agents apply `include_archived` and
  `created_at[gte|lte]`; Environments apply `include_archived` but no creation-time filters. See
  [`pagination-and-filters.md`](./pagination-and-filters.md).
- The in-sandbox bridge does not implement the Managed Agents tool-confirmation round trip, so
  `always_ask` tools are omitted from the SDK tool list rather than prompting.
- `colocated` rejects an Environment-supplied `image`. Remote providers expose no sealed setup
  namespace, so a custom image could race trusted resource and Skill materialization; operators
  change the catalog image at deployment time instead.
- Cloud `SandboxHandle.endpoint()` coverage — per-acquire image and port exposure in the E2B and
  OpenSandbox runtimes, plus a gated cloud e2e test.
- Scoped OIDC administrator roles are not implemented; admin OIDC carries `org:admin` or nothing.
- The OIDC `metadata` claim fallback is one opt-in per plane, so a plane that enables it must allow
  exactly one issuer; with several, the registry refuses to start. Trigger: a deployment that needs
  several issuers on one plane while one of them supplies claims only under `metadata`. Add a
  per-issuer opt-in rather than relaxing the single-issuer check. See
  [`workspace-administration.md`](./workspace-administration.md#oidc-claim-sources).
- The Session JWT's `llm_models` claim is the deployment policy (`SESSION_JWT_LLM_MODELS`)
  intersected with the session's Agent models; no workspace-level model policy narrows it further.
  Trigger: an organization that must restrict which models one workspace may use. Add the workspace
  policy as a further intersection in the same derivation. See
  [`auth-and-vaults.md`](./auth-and-vaults.md).
- Guardrail and model-price administration has no narrower delegation than `org:admin`: the admin
  routes check `guardrails:*` and `model_prices:*` scopes, but `registry:create-admin-key` rejects
  them in `ORCA_ADMIN_KEY_SCOPES` and admin OIDC accepts only `org:admin`. Trigger: an organization
  that must delegate guardrail or price management without granting `org:admin`.
- Audience-based workspace resolution (`OIDC_RESOLVE_WORKSPACE_BY_AUDIENCE`) resolves an
  organization only while it has exactly one active workspace, and an organization's `audience` is
  set only at creation: no route updates it and nothing backfills organizations created without one.
  Trigger: an organization in that mode needs a second active workspace, or an existing organization
  must adopt the mode. Persist an explicit default workspace per organization, so resolution keeps a
  referent when a second workspace exists, and give existing organizations a supported way to
  acquire an audience in the same change.
- `GET /v1/sessions/{id}/threads` lists threads newest-first (`created_at DESC, id DESC`), so the
  primary thread sorts last; Anthropic lists the primary thread first, then children in spawn order.
  The divergence is registered `fix-later` (`prose-threads-list-ordering` in
  `services/registry-service-ts/conformance-decisions.yaml`). Trigger: a client that depends on
  Anthropic's thread order, or the next change to the thread-list query.
- `user.interrupt` does not preempt a turn harness-server is driving. Event-source delivery is
  serialized per session and the dispatcher awaits the turn-driving `submit()`, so an interrupt
  normally reaches the harness after that turn has returned; the acceptance barrier still precedes
  any abort call when a query is active. (The registry pushes a runner-driven session's interrupts
  to its runner on a separate concurrent loop.) See
  [`event-processing-semantics.md`](./event-processing-semantics.md). Trigger: a client that must
  stop a harness-server turn mid-query. Promising active-query preemption needs a separate
  concurrent control channel into the dispatcher, plus runner fencing.
- Runner-driven sessions never receive acceptance markers: every `self_hosted` session, and cloud
  sessions of the harnesses the registry runs through a runner (`codex`, `cursor`, `pi`, `custom`,
  `mock`).
  Only the harness-server dispatcher appends `session.user_event_processed`; the registry's runner
  event bridge appends none. Their client events therefore keep `processed_at: null` and stay in
  the unprocessed-event gauges on `/metrics`. Trigger: a client or operator that relies on
  `processed_at`, or on those gauges, for runner-driven sessions. Append the acceptance marker from
  the runner path when the runner accepts each client event.
- Request-body validation is partial. The ts-rest contracts in `src/contracts/` define Zod schemas,
  but many Fastify handlers still validate by hand or fall through to flat errors, so
  Anthropic-style error envelopes are not complete on every route.
- The contracts are not what registers the Fastify routes; `test/unit/route-contract-parity.spec.ts`
  keeps the two in step rather than construction doing it.

**CI**

- The `coverage` job reports but does not block. The required checks are `test`, `integration`,
  and `lint-and-breaking`; a repo admin must add `coverage` for it to gate.
- Nothing measures whether moving the e2e suites off per-PR runs traded too much. The trigger to
  revisit is a stack regression reaching `main` and surviving past the next daily tick, or the
  `run-e2e` label going unused on PRs that later break `main` — either says the opt-in is not
  reaching the changes that need it.

## Codex SDK capability expansion

The managed Codex SDK integration does not yet support multimodal user input,
multiagent rosters, self-hosted separate execution, `system.message` companions,
or outcome commands. Both modes support durable stateful request budgets and reject
soft request approval thresholds and subagent budgets. Codex separate also rejects stateful tool policies and
response/model-call phases; it supports stateless request and tool phases. Colocated
Codex rejects general tool and response/model-call phases. Add the missing guardrail phases only after SDK model-call
interception exposes authoritative per-call usage and response boundaries. Add
self-hosted separate only after runner-host execution is distinct from the Sandbox
and tested across reconnects. Add system companions after native resume honors
updated developer instructions, and outcomes after a provider-neutral evaluator
is integrated. Both managed modes use the shared managed Skill catalog and
sandbox read tool, without native skill discovery.
Enable other capabilities only after content conversion or per-thread checkpoint ownership
has acceptance tests for permissions and reconnect recovery. Keep the capability
catalog and Agent validation in step with each implementation.

The Gateway image used by deployments must include the native Responses API
companion change before enabling `aiGateway.openai.enabled`. Update the pinned
release image after that Gateway release passes native SDK integration tests.

### Cloud Claude Code runner parity

Cloud `claude_code` retains the sandbox-harness HTTP bridge. Move its
`cloudExecutionOwner` to Registry only after session-runner supports the same
FUSE resource mounts, native subagents, output capture and durable stateful
budget enforcement, and the OpenSandbox real-agent suite passes through that path.

Before enabling runner-owned cloud harnesses in a deployment, publish and pin the
Orca Environment image (`services/environment-image/`) in that provider and wire
its Environment launcher configuration. Validate the worker/runner tunnel and
harness on the actual E2B or OpenSandbox deployment.

## Pi SDK extensions

`pi_sdk` ships cloud separate, cloud shared colocated and self-hosted colocated
execution with the native Pi 0.87.1 SDK and its admitted static API-key model catalog. The older `pi`
harness remains the separate CLI RPC integration.

- **Native Pi Gateway release:** Pi's isolated native route requires a Gateway build
  that includes native Pi provider routing — `native_api_key` destinations and the four
  protocol observers. The chart's default released image is not evidence of support.
  Trigger: publish and pin a release containing the native proxy implementation before
  enabling `aiGateway.piProviders` in production.
- **Additional Pi protocols and authentication:** Mistral Conversations, Pi Messages,
  Bedrock, Vertex, Azure deployment configuration, Cloudflare account discovery and
  OAuth/token-exchange providers remain outside the static-key transport catalog.
  Trigger: a deployment requires one of these and protocol usage validation plus
  credential isolation have end-to-end acceptance tests.
- **Automatic compaction:** enable it after its extra model requests have explicit accounting
  and recovery tests. Managed Pi currently disables auto-compaction, retries and cache warming.
- **Pi multiagent and broader stateful phases:** add only after the native adapter supports
  corresponding managed child-session and durable enforcement contracts. Current request
  budgets operate at turn boundaries, as in Codex SDK.
